# Ledgerline - Edge-Case Analysis

Related: [LLD](03-lld.md) | [Technical architecture](04-technical-architecture.md) | [Decision log](decision-log.md)

For every case: how it is **detected**, what the **system does**, what the **user sees**, and where it is **implemented and tested**.

## Summary table

| # | Case | Detection | System behaviour | What the user sees | Bill status |
|---|------|-----------|------------------|--------------------|-------------|
| 1 | **Corrupt PDF** | `pypdf` raises while opening or the page count is 0. Image bytes fail Pillow `verify()`. | `UnreadableDocumentError`. No retry (retrying cannot help). `error_message` set. Audit `extraction_failed`. | Upload row and queue show "Extraction failed: the file appears to be damaged or is not a valid PDF. Please re-export or re-scan and upload again." | `failed` |
| 2 | **Password-protected PDF** | `reader.is_encrypted` is true and `decrypt("")` fails | `PasswordProtectedDocumentError`. No retry. Passwords are not accepted or stored in the MVP. | "This PDF is password-protected. Remove the password (print to PDF) and upload again." | `failed` |
| 3 | **Scanned image, no text layer** | PDF text has fewer than 40 non-whitespace characters per page on average (D-052) | Pages rendered to PNG at 150 DPI (first 5 pages) and sent to the vision model. `extraction_method = vision`. Confidence comes from the model, not raised by grounding. Low-confidence fields raise warnings. | Bill shows the method "Scanned (vision)". Low-confidence fields are highlighted in amber for verification. | `needs_review` |
| 4 | **Multi-page invoice** | `page_count > 1` | Text path: text from **all** pages is concatenated with page markers (capped at 60,000 chars), so line items across pages are captured. Vision path: up to 5 pages are sent in one request, and `pages_processed` is stored on the bill. The full document is always shown in the preview. | All line items from all pages. For scans longer than 5 pages, a banner reads "Pages 1 to 5 of 8 were read. Check the remaining pages for extra line items." | `needs_review` |
| 5 | **Duplicate invoice uploaded twice** | (a) The same SHA-256 file hash in the company. (b) The same vendor GSTIN + invoice number + total on another non-rejected bill (D-027). | Both bills are processed. A `duplicate_invoice` **error** finding goes on the **later** upload only, naming the earlier bill and its upload date, so the original stays approvable (D-066). Approval is blocked (D-021). | Red finding: "This looks like a duplicate of invoice INV-1043 from Acme Traders uploaded on 02 Oct 2026 (status: Approved). Reject it unless this is a genuinely separate bill." The reviewer rejects with reason "Duplicate". | `needs_review`, then `rejected` |
| 6 | **Invalid GSTIN** | Regex, state code (01-38, 97, 99), and mod-36 checksum fail | `gstin_format` **error**. The vendor is **not** auto-created (D-023). The bill stays unlinked. The reviewer can correct the GSTIN, which triggers vendor matching and re-validation. | "Vendor GSTIN '27AAPFU0939F1Z9' is not valid: the check digit does not match. Verify it against the invoice." | `needs_review` |
| 7 | **Line items do not add up** | Sum of line amounts compared with the subtotal (tolerance Rs 1). Per line, `qty x rate` compared with the amount. | `line_item_arithmetic` **error** with the computed and stated values. The reviewer can fix a line or the subtotal, which re-validates. | "Line items add up to Rs 10,500.00 but the subtotal says Rs 10,000.00 (difference Rs 500.00)." | `needs_review` |
| 8 | **Tax does not match the rate** | Effective rate = (CGST+SGST+IGST) / subtotal is not within 0.1 pp of a GST slab. Or CGST is not equal to SGST. | `tax_rate`: **error** if CGST is not equal to SGST. **warning** if the effective rate is non-standard (it may be a legitimate mixed-rate invoice). | "Total tax is 15.3% of the subtotal, which is not a standard GST rate (0, 0.25, 3, 5, 12, 18, 28, 40%). Check the tax amounts." | `needs_review` |
| 8b | **Wrong tax type** (IGST on an intra-state supply or the reverse) | Vendor GSTIN state compared with the buyer GSTIN state (falling back to the company GSTIN) | `tax_type` **error** | "Vendor (Maharashtra, 27) and buyer (Karnataka, 29) are in different states, so IGST should apply, but CGST/SGST was charged." | `needs_review` |
| 9 | **Vendor does not exist yet** | No vendor row with `(company_id, gstin)` | If the GSTIN is valid, create the vendor (legal and display name from the invoice, state from the GSTIN) and audit `vendor_created`. A unique constraint plus a savepoint and reload handles two concurrent extractions creating the same vendor. | The bill timeline shows "System added new vendor Acme Traders Pvt Ltd from this invoice". The vendor appears on the Vendors page, where the brand name can be edited. | `needs_review` |
| 10 | **OpenAI timeout or rate limit** | `openai.APITimeoutError`, `RateLimitError`, `APIConnectionError`, 5xx mapped to `ProviderTransientError` | The SDK retries twice internally. Then the job retries with backoff (2 s, 8 s), 3 attempts total (D-049). The bill goes back to `queued` between attempts. After the final failure: `failed`, retryable. Review of other bills is unaffected. | "Extracting..." takes longer. If all attempts fail: "The AI service is busy or unavailable. Click Retry extraction." | `queued` -> `failed` |
| 11 | **Very large files** | Client pre-check plus server streaming read with a hard cap (`MAX_UPLOAD_MB`, default 15 MB). More than 20 files per request is rejected. Many-page PDFs: text capped at 60k chars, vision capped at 5 pages, images downscaled to a max of 2000 px. | An oversized file is rejected per file (`file_too_large`) **without** failing the other files. Bytes are never fully buffered past the cap. | Row: "File is 22.4 MB, the limit is 15 MB. Compress or split the PDF." | not created |
| 12 | **Two reviewers editing the same bill** | Optimistic locking: every write sends `version`. The server compares it under `SELECT ... FOR UPDATE` (D-047). | The first write wins and the version increments. The second gets `409 version_conflict`, and nothing is overwritten. Approve and reject are also version-checked, so a bill cannot be approved while someone else just changed it. | Second reviewer: toast "Someone else updated this bill. You are now seeing the latest version." The latest data and audit timeline (showing who changed what) are shown. They re-apply their edit if still needed. | unchanged |
| 13 | **Expired login token** | PyJWT `ExpiredSignatureError` -> `401 token_expired` | Request rejected. No partial work. | The frontend clears the session, keeps the current path, and redirects to `/login?next=/review/...` with "Your session expired. Please sign in again." Unsaved field edits stay in the input until redirect (and are lost; noted as a limitation). | n/a |
| 14 | **Invalid or tampered token** | Bad signature, malformed token, missing claims, or the user deleted or deactivated -> `401 invalid_token` | Request rejected. Logged as a warning with the request id (not the token). | Redirect to login: "Please sign in." | n/a |

## Additional cases covered

| Case | Behaviour |
|------|-----------|
| Unsupported file type (for example `.docx`, or `.pdf` that is really a ZIP) | Magic-byte sniffing returns `unsupported_file_type` for that file only. |
| Zero-byte file | Rejected as `unsupported_file_type` ("File is empty"). |
| LLM returns malformed or partial JSON | Structured outputs make this rare. A Pydantic validation failure maps to `ProviderPermanentError` and `failed` with retry available. |
| LLM returns a value in the wrong format (for example date "5th Oct 26", amount "Rs 1,23,456.00") | The normaliser parses common Indian formats (`dd/mm/yyyy`, `dd-MMM-yyyy`, lakh commas, the Rs symbol). If unparseable, the field is null, the raw value is kept in `raw_extraction`, and the field gets confidence 0 and a warning. |
| Invoice in a currency other than INR | Out of scope (D-105). Extracted as-is. A non-INR currency symbol in the text raises a warning. |
| Server restarts mid-extraction | On startup, bills in `queued` or `processing` are re-enqueued (D-048). The handler is idempotent. |
| Reviewer edits a bill that is still processing | `409 invalid_state`. The UI disables editing until `needs_review`. |
| Cross-tenant access (guessing another company's bill id) | The repository filters by `company_id`, so the response is `404 not_found` (no existence leak). Covered by a test. |
| Correcting vendor GSTIN to a new valid GSTIN | Vendor matching re-runs: it links the existing vendor or creates one. Audit records the vendor link change. |
| Bill with no line items (summary invoice) | `required_fields` warning "No line items were found". The arithmetic rule is skipped. |
| Round-off line ("Round off: 0.40") | A total difference of Rs 1 or less is reported as **info**, not an error (D-029). |
